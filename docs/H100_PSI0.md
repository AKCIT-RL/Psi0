# Treino Psi0 na H100 com Slurm e W&B

Este runbook descreve o pipeline reproduzivel validado para treinar Psi0 em uma
H100 com Slurm, Apptainer e W&B. Siga sempre as politicas de uso, armazenamento
e seguranca do cluster onde o job sera executado. Documentos operacionais
internos ou privados nao fazem parte deste guia e nao devem ser versionados.

Todos os comandos partem da raiz do repositorio:

```bash
export PROJECT_DIR="$(git rev-parse --show-toplevel)"
cd "$PROJECT_DIR"
mkdir -p logs
```

Os scripts incluidos usam `h100n2` como particao validada. Em outro cluster,
substitua as diretivas `#SBATCH --partition` pelos valores aprovados pelo
administrador antes de submeter.

## Imagem

Use somente a imagem de desenvolvimento, que inclui FlashAttention:

```text
docker://rafaeljose/industrial_humanoids:psi0-train.gr00t_devel
```

A tag `psi0-train.gr00t` nao e adequada ao treino Psi0 porque nao contem
`flash_attn`, exigido por `src/psi/trainers/finetune.py`.

Submeta o pull como job CPU:

```bash
sbatch scripts/train/psi0/pull_h100_image.slurm
```

O job grava a imagem e seu checksum em:

```text
containers/industrial_humanoids_psi0-train.gr00t_devel.sif
containers/industrial_humanoids_psi0-train.gr00t_devel.sif.sha256
```

## Gate 1: runtime H100

Depois do pull concluir com estado `COMPLETED`, submeta:

```bash
sbatch scripts/train/psi0/smoke_h100_runtime.slurm
```

O smoke exige uma H100 `sm_90`, importa o codigo Psi0 montado do checkout e
executa um kernel FlashAttention em BF16. O gate passa somente se o log registrar
o device H100, capability `(9, 0)`, versoes de PyTorch/FlashAttention e tensor de
saida finito.

## Entradas do treino

Antes do smoke de treino, devem existir:

```text
data/<dataset>/meta/info.json
data/<dataset>/meta/stats_psi0.json
data/<dataset>/meta/episodes.jsonl
data/<dataset>/meta/tasks.jsonl
psi_home/cache/checkpoints/psi0/pre.fast.1by1.2601091803.ckpt.ego200k.he30k
psi_home/cache/checkpoints/psi0/postpre.1by1.pad36.2601131206.ckpt.he30k
secrets/psi0.env
```

O dataset precisa ser LeRobot v2.1 validado para Psi0. Registre o `repo_id` e a
revision imutavel do Hugging Face antes de materializa-lo sob `data/`.

O arquivo `secrets/psi0.env` deve ter permissao `600` e permanecer ignorado pelo
Git. Ele deve definir, sem imprimir os valores:

```text
WANDB_API_KEY
WANDB_ENTITY
WANDB_PROJECT
HF_TOKEN
```

O cache Hugging Face fica sempre em `cache/huggingface`; runs ficam em `.runs` e
o cache W&B em `cache/wandb`.

Para o dataset WMO totes e os pesos baseline oficiais, use:

```bash
sbatch scripts/train/psi0/prepare_h100_totes.slurm
```

O job fixa o dataset em `219d98f9228f9d2db41d723a56744f3b9093353a`,
baixa o subtree Psi0 pronto, resolve e registra o commit atual do repositorio de
modelos, baixa os dois diretorios de checkpoint listados no README e executa o
validador de modalidade antes de concluir.

## Gate 2: smoke de treino

O smoke usa uma H100, batch 1, dois steps, um batch de validacao e checkpoint a
cada step:

```bash
DATASET_NAME=<dataset-local> \
DATASET_REPO_ID=<org/dataset> \
DATASET_REVISION=<commit-hf> \
EXP_NAME=<nome-unico>-smoke \
SMOKE_MODE=1 \
sbatch scripts/train/psi0/submit_h100_psi0.slurm
```

O gate passa somente quando:

1. O run W&B e criado no entity/projeto esperado.
2. Os dois steps produzem loss finita.
3. Ha pelo menos uma metrica `eval/*`.
4. O checkpoint final contem modelo e estado de otimizador/scheduler.
5. Dataset, split, dimensoes e commit do codigo aparecem nos metadados do run.

## Gate 3: retomada

Submeta outro smoke apontando `RESUME_FROM_CHECKPOINT` para o caminho do
checkpoint dentro do container, sob `/workspace/.runs`. Confirme no log que o
step inicial corresponde ao checkpoint e que o mesmo run W&B foi retomado.

## Treino completo

Somente depois dos tres gates:

```bash
DATASET_NAME=<dataset-local> \
DATASET_REPO_ID=<org/dataset> \
DATASET_REVISION=<commit-hf> \
EXP_NAME=<nome-unico-h100> \
sbatch scripts/train/psi0/submit_h100_psi0.slurm
```

Defaults: uma H100, batch efetivo 8, BF16, 50 epocas, seed de treino `292285`,
split de episodios 90/10 com seed `42`, validacao a cada 2.500 steps e cinco
checkpoints preservados. Use `RESUME_FROM_CHECKPOINT` para continuar uma
execucao interrompida.

Nao considere um treino validado apenas por estar em `RUNNING` ou por terminar
com exit code zero. Confirme curvas W&B, metricas de validacao, checkpoint
carregavel e associacao ao dataset/revision corretos antes de iniciar a
avaliacao no SIMPLE.

## Smoke de avaliacao no SIMPLE

O smoke WMO usa um checkpoint completo, inicia o servidor Psi0 dentro da mesma
SIF do treino e executa um episodio headless no SIMPLE. Construa a imagem e
encadeie a avaliacao:

```bash
BUILD_JOB=$(sbatch --parsable scripts/eval/build_simple_wmo_h100.slurm)
sbatch --dependency="afterok:$BUILD_JOB" \
	scripts/eval/smoke_simple_wmo_h100.slurm
```

O resultado fica em `eval/results/wmo-totes-20260807/slurm-<job-id>/`. O smoke
so e aprovado quando existem health check do servidor, `eval_stats.txt` com um
episodio e pelo menos um MP4 nao vazio. Esse episodio usa dados de treino e
valida apenas a integracao; nao e uma medida de generalizacao da politica.
